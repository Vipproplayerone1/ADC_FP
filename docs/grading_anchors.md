# Track 3 Grading Anchors — Evidence Map

This document maps each row of the **Track 3 Requirement Mapping** table in `README.md` to the concrete code, data, or output that satisfies it.

| # | Requirement | Where it is satisfied |
|---|---|---|
| 1 | Choose one academic subject | The demo set covers Machine Learning (`data/raw/uploaded_pdfs/Lecture_0[2-6]_*.pdf`, generated by `scripts/generate_demo_pdfs.py`). The subject is **not hardcoded** anywhere — see #3. |
| 2 | Use 5–10 lecture slide PDFs | 5 demo PDFs ship via `scripts/generate_demo_pdfs.py` covering 41 chunks across 41 pages. |
| 3 | System must work on **any** uploaded set | `app/services/pdf_loader.py`, `text_chunker.py`, `embedding_service.py`, `vector_store.py` are subject-agnostic. No string in the codebase mentions specific lecture topics outside the demo data and the eval CSVs. |
| 4 | Input: PDF + natural-language query | `POST /upload` (multipart PDFs) → `app/api/upload_routes.py`. `POST /chat` (JSON `{query}`) → `app/api/chat_routes.py`. Streamlit surfaces both in `frontend/streamlit_app.py`. |
| 5 | Document ingestion pipeline | `pdf_loader.load_pdf_pages` → `text_chunker.chunk_pages` → `embedding_service.Embedder.embed_texts` → `vector_store.ChromaStore.add_chunks`. End-to-end driver: `scripts/ingest_documents.py`. |
| 6 | RAG pipeline | `app/services/retrieval_service.retrieve` embeds the query with the same model used at indexing time, queries Chroma for top-k, and `format_context` builds the prompt context. `rag_service` then calls the LLM with the templated prompt. |
| 7 | Transformer-based LLM | Llama 3.1 (8 B parameters, decoder-only Transformer) via the local Ollama daemon. Set in `OLLAMA_MODEL`. |
| 8 | Contextual Q&A | `app/services/rag_service.answer_question` + `app/prompts/qa_prompt.txt`. Refusal phrase is enforced via prompt: `"I could not find enough information in the uploaded documents."` |
| 9 | Automatic MCQ generation | `app/services/mcq_service.generate_mcqs` + `app/prompts/mcq_prompt.txt`. JSON-mode call, Pydantic validation against `MCQItem`, automatic source fallback to the top retrieved hit, one retry on bad JSON. |
| 10 | Output includes source references | Every `ChatResponse`, `SummaryResponse`, and `MCQItem` carries `Source{file_name, page, chunk_id}`. Deduplication by `(file_name, page)` in `rag_service._sources_from_hits`. |
| 11 | Deployment: FastAPI + Streamlit | Backend: `app/main.py` (FastAPI), 5 endpoints (`/`, `/upload`, `/chat`, `/summary`, `/mcq`). Frontend: `frontend/streamlit_app.py`, 3 tabs (Q&A, Summary, MCQ). |
| 12 | Rigorous evaluation | `scripts/run_evaluation.py` with 4 subcommands (`retrieval`, `qa`, `summary`, `mcq`, `all`). Metrics: Precision@K, Recall@K, MRR, Hit@3, Hit@K, QA Accuracy, ROUGE-L, BLEU, grounded_rate, ROUGE-1/2/L for summaries, heuristic MCQ rubric, per-step latency. Output: `docs/evaluation_report.md`. |

## Architectural Compliance with `CLAUDE.md`

| Rule from CLAUDE.md | Where it is satisfied |
|---|---|
| Services are pure (no FastAPI imports) | `grep -l "fastapi" app/services/*.py` returns no matches. |
| Routes are thin — parse → service → Pydantic | Each `app/api/*.py` file is under 25 lines and only does request validation + service delegation. |
| Schemas in `app/schemas.py` | All request/response models live there; no raw dicts cross the API boundary. |
| Prompts as templates in `app/prompts/*.txt` | 3 prompt files, loaded via `prompt_loader.load_prompt`, never inlined. |
| `pydantic-settings` config | `app/config.py` exposes a single `Settings` class loaded from `.env`. No `os.getenv` scattered. |
| Single embedding model for index + query | `Embedder._model` is an `lru_cache` of size 1 reading from `settings.embedding_model`. |
| Mandatory metadata: `file_name`, `page_number`, `chunk_id` | Enforced in `text_chunker.chunk_pages`; verified by `tests/test_text_chunker.py::test_chunks_carry_required_metadata`. |
| Source citations on every answer | `_sources_from_hits` is called for both Q&A and Summary; MCQ has its own source field. |
| Refusal phrase when context insufficient | Hard-coded in `app/prompts/qa_prompt.txt` and exercised by the live smoke test. |

## Test Coverage

| Module | Test file | What it asserts |
|---|---|---|
| `pdf_loader` | `tests/test_pdf_loader.py` | Extracts text + page metadata from a synthetic 2-page PDF; returns empty list for missing files. |
| `text_chunker` | `tests/test_text_chunker.py` | Chunks carry `file_name`, `page_number`, `chunk_id`; chunk_size respected within tolerance; empty pages produce no chunks. |
| `vector_store` | `tests/test_vector_store.py` | Round-trip add + query; query on empty store returns `[]`. |
| `rag_service` | `tests/test_rag_service.py` | Q&A returns sources with file + page; summary returns sources; refusal path with empty store. |
| `mcq_service` | `tests/test_mcq_service.py` | Parses valid JSON; retries on bad JSON; injects source fallback when LLM omits it. |
| **API routes** (integration) | `tests/test_api_routes.py` | `GET /` health; `POST /upload` indexes a real PDF and rejects non-PDFs; `POST /chat`, `POST /summary`, `POST /mcq` return correct shapes with mocked LLM; request validation rejects bad inputs. |

Total: **22 tests across 6 files.** Run with `pytest -q`.

## Reproducing the Evaluation

```powershell
# Prereqs: setup.ps1 done, Ollama running, llama3.1:8b pulled
ollama pull llama3.1:8b
.venv\Scripts\python.exe scripts\generate_demo_pdfs.py
.venv\Scripts\python.exe scripts\ingest_documents.py --input_dir data\raw\uploaded_pdfs
.venv\Scripts\python.exe scripts\run_evaluation.py all
# -> docs\evaluation_report.md updated with fresh metrics
```
